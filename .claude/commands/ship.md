## The loop

**1. Implement.** Make the change. One concern at a time.

**Before** implementing, if the change adds a new trust boundary — an LLM
call, forking, payments, a new role, a new external service, or a new way for
one user's content to reach another — call `security-reviewer` in **threat
model mode** with the feature's design. Build against the design requirements
it returns; step 5 will check the code against them. Ordinary changes inside
existing boundaries skip this.

**2. Cover it, if it has testable logic.** If the change added or changed a pure
function or a component's behaviour in `frontend/`, call the `test-author`
subagent — then call `test-verifier` on what it wrote.

Give `test-author` the **specification**, not the diff: what the thing should do,
its edge cases, what should happen when input is empty or malformed. It
deliberately does not read implementations, because a test written from the code
just transcribes the code's bugs.

`test-verifier` then breaks the source on purpose and confirms the new tests go
red. If it reports **NOT VERIFIED**, the tests are decoration — send them back to
`test-author` with what the verifier found.

Skip both for changes with no testable logic: styling, copy, config, docs,
backend-only work.

**3. Verify.** Call the `test-runner` subagent. It runs Go build, vet and tests
in `backend/`, then typecheck, tests, lint and the production build in
`frontend/`, and reports failures with `file:line`.

**4. Fix and repeat.** Go back to step 3 after each fix.

**Stop after 3 failed attempts.** Do not keep going. Report what is still red,
what you tried, and hand back. An unbounded loop on a problem the model cannot
solve burns an hour and a lot of tokens to arrive at the same place.

**5. Security review.** Once `test-runner` is green, call the
`security-reviewer` subagent on any change that touches:

- `backend/` — handlers, `routes.go`, `db/query.sql`, migrations, middleware
- Next.js route handlers (`app/**/route.ts`), `"use server"` files, or
  `frontend/utils/supabase/`
- authentication, uploads, emails, redirects, or how user content is rendered
- config, environment variables, `.gitignore`, or anything under `scripts/`

Tell it what changed and why. Skip it for pure styling, copy, docs and
test-only changes.

On **BLOCK**, fix the Critical/High findings that belong to this change, then
go back to step 3 — `test-runner` first, then `security-reviewer` again. Those
rounds count toward the same 3-attempt cap. If a fix needs a product decision
(who should be allowed to do X), do not guess: stop and put it to the user.

**PASS WITH FINDINGS** does not block. Pass the Medium/Low and pre-existing
findings on to the user in your hand-back, verbatim enough to act on.

**6. Look at it — but only when the change is visual.** Call the `ui-reviewer`
subagent when **both** hold:

- the change touched files under `frontend/app/` or `frontend/components/`, and
- the local dev server answers on `http://localhost:3000`

Skip it otherwise. A browser review of a backend, script or docs change is pure
cost, and `ui-reviewer` cannot review a server that is not running — it will say
so and stop, which wastes a turn.

Its findings are **advisory**. Fix what is genuinely broken; for anything that is
a matter of taste, report it and let the user decide. Never treat it as a gate:
`test-runner` is the gate, and a screenshot is a second opinion.

**7. Record, but only sometimes.** If a failure had a cause that a future session
would plausibly hit again — a constraint of this codebase, not a slip — call the
`memory-keeper` subagent. Do not call it for typos. A memory directory full of
noise is read by nobody.

**8. Hand back.** Do not commit, push or deploy. Deployment order here is strictly
migration (Supabase SQL editor) → backend (VPS) → frontend (Vercel push), and it
is the user's call when to start it.

**If the change touches a migration or `backend/`, say so in bold in your final
message**, and name the migration file. Shipping the backend before its migration
has 404'd this site before.

## What the gate does not cover

`test-runner` builds, vets and tests the backend locally (Go 1.27 is installed),
and runs the feed integration tests when the local Supabase is up. What it cannot
see:

- **Generated row types.** `backend/pkg/db/` is generated by sqlc — never
  hand-edit it; regenerate through WSL (see CLAUDE.md). sqlc v1.21 types `CASE`
  as `interface{}`, `NULLIF` as `bool`, `COALESCE` as non-null, and a `UNION`
  from its first branch only. Each compiles cleanly and fails at runtime as a
  500, so after any query change read the generated `...Row` struct.
- **Handlers outside the integration tests.** Against a real database run:
  feed, trending and popular tools, and — through the real router — create
  post, star, the tool-ticket resolutions, tool page edits and search
  (`characterisation_integration_test.go`). Anything else needs the endpoint
  hit once after the change.
- **Security.** A green gate says nothing about who may call an endpoint —
  that is what step 5 is for. `routes_test.go` does pin each route's auth
  group, so a route moved between groups fails the gate.
